# Starting a project well

Draft specification for v0.5. This page describes intended behaviour, not functionality already shipped.

## Starting with nothing

Offer a broad starting basket: the information and outcomes worth checking to launch the project. Explain the path and suggest where to begin. Let the designer discover missing information through the work; a long form must not be the entry requirement.

The following is a proposed checklist to validate against the supplied framework and real projects.

| Outcome to check | What should be clear | Useful response when missing |
| --- | --- | --- |
| Purpose and decision | Why the project exists, the problem/opportunity and the decision to support | Frame the request with the product team |
| Users and situation | Who is affected, their task/context and important differences between profiles | Clarify the population and missing perspectives |
| Current knowledge | Facts with sources, assumptions, unknowns and existing work | Review evidence and record uncertainty |
| Expected success | Intended improvement, observable signals and any credible reference point | Define outcomes and establish what needs measuring |
| Scope and influence | What is fixed, what can change, boundaries and dependencies | Agree a mandate or a useful limited contribution |
| People and ownership | Decision owner, contributors, approval roles and critical expertise | Resolve responsibilities and involve the needed roles |
| Access and practical feasibility | User/evidence access, deadline, available effort and relevant permissions | Confirm access, narrow scope or request support |
| First course of action | Prioritised unknowns, next steps, owners and review dates | Build the initial plan and address blockers |

The framing canvas supports several of these outcomes. It should be available from the proposed work without requiring the designer to start by browsing the entire guide library.

## Checking progress

Proposed outcome states: Not checked, Met, Needs work, Blocked and Not applicable. A short checkbox-style interaction should handle common cases; allow a reference or reason when useful. The exact labels require interface review.

- Existing work can satisfy an outcome after explicit review. It may live outside this tool.
- An activity or template is a possible way to achieve an outcome. Reading it or filling every field does not automatically validate the result.
- Explain why an item is essential now, conditional or optional. Do not require constrained alignment on an open project or blocker resolution when no blocker exists.
- When context changes, identify affected checks for review and preserve the original work.

## Entering later

Ask what is already in place and check only the dependencies of the next useful action. A person with research data should reach analysis support promptly. A person with findings but no decision should reach a focused blocker review.

## Escalation

Missing purpose, access or ownership should trigger a visible action. Distinguish something not yet checked from a confirmed blocker. A blocker record should identify what is affected, the next response, responsible role, review date and resolution. The framework should support proceeding with explicit limits, obtaining support, reframing, pausing or stopping where appropriate.

Role-specific organisational rules need confirmation before implementation. See [decisions and questions](decisions.md).

## Acceptance examples

- A newcomer sees the broad launch checklist and a useful first action without selecting a research method prematurely.
- Existing framing and mandate can be acknowledged without repeating their workshops.
- Missing user access stays visible when it affects the next action; it does not disappear merely because the stage changes.
- A clear open project can finish framing without completing conditional constrained-project work.
- An unresolved essential has an action and owner or a visible request to establish one.
