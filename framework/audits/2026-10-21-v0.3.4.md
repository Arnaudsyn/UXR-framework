# Research Compass: framework audit for v0.5

Reviewed 21 October 2026. Production version: **0.3.4**, commit **1fd0686e1f374844b652c024dd11019cf9fca0f8**.

**The next release needs a layer that records project outcomes and derives the next useful action.** The current content, guided activities and portable workspace provide useful building blocks. Their presence does not yet establish a working decision framework.

This audit records the v0.3.4 baseline. The [framework brief](../vision.md) and [backlog](../backlog.md) track the evolving v0.5 direction, including project launch and the research builder. The live application was not changed by this review.

## What was checked

- The deployed kickoff experience, current application logic, content structures, storage model, progress calculations, method selection, advice rules, and existing automated checks.
- Ten reproducible scenario groups using isolated in-memory projects. No real visitor projects were edited. The [diagnostic script](audit-v0.3.4.cjs) and its results are saved beside this report.
- The existing rendered framework reference, particularly readiness branches, standard/limited routes, escalation/stop, evidence-quality loops, and the decision checkpoint before restitution. These distinguish the source framework from a list of activities.
- The latest requirement: help a UX designer enter at any point, acknowledge completed work, select a feasible route, identify the next step, and address blockers with the product team.

The existing regression suite passes. The new diagnostic also passes: its assertions reproduce the current gaps, rather than claiming that v0.5 requirements are satisfied. This was not a participant usability study, a complete accessibility audit, or a validation of every methodology detail in the PDFs.

## Findings and fixes

### 1. P1 — The recommended starting point repeats the declared stage

**Observed:** Complete both readiness activities. The homepage still links “Go to suggested starting point” to readiness. The completed readiness card loses its “Start here” label, leaving no suggested card. The timeline also keeps allocating time to completed work.

**Cause:** `recommendation()` reads the declared stage and a few constraint flags. It does not consider completion, prerequisites, checklists, evidence or unresolved issues. `timelinePlan()` also works from the declared stage. Reproductions A01 and A09.

**Fix:** Derive a next action from relevant unmet outcomes, unresolved dependencies and feasible work. The declared stage supplies entry context, not the entire answer. When a stage is satisfied, identify the next relevant outcome. A late-stage user should get a targeted gap check, without a requirement to repeat every earlier activity.

**Acceptance:** Completing readiness advances the recommendation; arriving at analysis with an existing plan and evidence leads to analysis; a single missing prerequisite offers a focused repair; a complete project offers closeout/reuse rather than another research cycle.

### 2. P1 — Objectives have no checkable outcome state

**Observed:** Objectives contain explanatory text and guide links. Their achievement cannot be recorded. Activity completion can be toggled with empty notes and unchecked criteria. Conversely, ticking all moving-on checks does not affect completion or recommendations. Reproductions A02 and A10.

**Cause:** The data model stores activity IDs in `done`, independent checkboxes in `checks`, and text in notes/templates. It has no record of an achieved project outcome. The current regression tests explicitly check that objectives lead to guides.

**Fix:** Give each stable outcome a short assessment, for example “The decision this research must inform is clear.” Let users record **Met / Needs work / Blocked / Not applicable**, with an optional reference or reason. Keep activity execution separate from outcome achievement. An existing brief or prior study may satisfy an outcome without running a workshop here.

**Acceptance:** An objective can be acknowledged from the stage page; its state survives reload/export/import; an unsupported or blocked criterion remains visible. Completing an activity offers an outcome review. Filling text, visiting a guide or finishing slides never silently establishes that an outcome is met. Any exception is explicit and reviewable rather than a forced universal lock.

### 3. P1 — All 20 activities count towards everyone's progress

**Observed:** An open project with framing and mandate complete remains at 2/3 kickoff because “Align a constrained project” is unfinished. Sharing requires “Resolve a decision blocker” even when the decision is already made. Quantitative analysis is also included in the universal activity total. Reproduction A03 and content inspection.

**Cause:** Stage completion requires every activity assigned to that stage. There is no applicability or “not needed” state. “Standard” and “focused” routes currently change labels/advice rather than the activity structure.

**Fix:** Separate required outcomes from possible ways to achieve them. Build a relevant activity shortlist with reasons. Constrained alignment applies when constraints require it; blocker resolution applies when a blocker exists; analysis activities follow the evidence actually available. Preserve access to the complete library.

**Acceptance:** A clear, open project can complete kickoff without a constrained-alignment session. A decision-ready project can finish sharing without blocker resolution. Progress measures relevant outcomes; optional activities do not penalise completion. Changes to applicability retain past work and record the reason.

### 4. P1 — Feasibility warnings do not shape the proposed work

**Observed:** A measurement project ending in two weekdays produces exactly the same method cards and planning activities as the same project with a long deadline. Only the timeline warning changes. Reproduction A04.

**Cause:** Method ordering uses intent, problem types, access and testable material. The deadline, available effort, recruitment lead time, existing usable data and review capacity do not determine feasibility. Project size/impact and intended strength of the claim are not captured structurally.

**Fix:** Assess the intended decision and claim, available evidence, remaining effort, access and deadline before proposing methods. Offer a feasible first action, explain what it can support, and identify what requires more time or specialist review. Ask only the missing question needed for that choice; keep advanced detail optional.

A short project can still use descriptive existing numbers. A large project does not automatically require population inference. The current site does **not** explicitly mandate a statistically representative study for every small project; the verified fault is that the proposed work does not change with feasibility.

**Acceptance:** A deadline that cannot accommodate new fieldwork changes the proposal and records the remaining limitation. Population-level claims require an explicit feasibility/research-design review. Essential interpretation and decision time remain part of the plan. No arbitrary population-size threshold certifies a suitable method.

### 5. P1 — Escalation is prose, with missing automatic triggers

**Observed:** An empty decision does not activate the “question or decision is unclear” advice. In collection that issue is not even offered. No-user-access advice appears in planning but disappears in kickoff and sharing. The homepage only supplies a generic route label. Reproductions A05, A06 and A10.

**Cause:** `activeDifficulties()` infers some flags and filters them by stage. An unclear decision is manual. There is no persistent escalation record, responsible role, review date or resolution state. Free-text escalation notes exist in some activities; those cannot drive the route.

**Fix:** Add a persistent blocker/action record: trigger, affected outcome or decision, consequence, proposed response, responsible role, next review and status. Make unresolved decision-critical issues visible wherever they affect the next action. Distinguish **unknown → check it**, **needs work → address it**, and **blocked → seek a decision/support**.

**Acceptance:** Missing purpose first proposes framing; unresolved purpose or missing authority offers escalation to the appropriate product/design role. Missing access prompts an access action or an explicitly limited evidence route, depending on the claim. Where no useful decision remains open, allow a pause/reframe/stop decision. Navigation stays open; the product explains the consequences of proceeding.

### 6. P2 — Advice can hide a more serious warning

**Observed:** In planning, record stale evidence and an unclear question, with user access set to none. The two visible cards are the first two advice entries. The no-access warning is behind “See all 3 relevant advice cards.” Reproduction A07.

**Cause:** Advice is shown in content-file order and truncated to two cards. Severity and impact on the current action are not used.

**Fix:** Prioritise blockers affecting the proposed next action, then warnings and useful advice. Keep unresolved blocking issues visible without expanding a list. Do not treat severity labels alone as a substitute for decision impact.

**Acceptance:** Adding an informational issue cannot displace a prerequisite blocker. The visible card explains why it matters now and provides a specific action.

### 7. P2 — Existing work, template drafts and framework progress are disconnected

**Observed:** Filling every framing-canvas field leaves all checks and activity progress untouched. A person joining near the end can choose a stage, but cannot acknowledge a set of already achieved outcomes in one review. They must open activities to mark them complete. Reproductions A08/A10 and form inspection.

**Fix:** Add a short “What is already in place?” assessment and an explicit “Review this output against the outcomes” action from templates and guided activities. Reference an existing document or approved repository; copying participant evidence into the tool is unnecessary. Template drafts remain drafts until reviewed.

**Acceptance:** A user brings an existing framing document, confirms the relevant criteria and proceeds without duplicating it. A saved canvas can be linked to a framing outcome. Context changes flag affected assessments for review without discarding drafts or rewriting history.

### 8. P2 — The timeline implies more planning precision than the route supports

**Observed:** Completing every activity leaves the same schedule from readiness through sharing. Allocation uses fixed stage weights, including one day per stage before distributing the remainder. Reproduction A09.

**Fix:** Base the schedule on relevant remaining work and confirmed availability. Until that exists, keep it explicitly illustrative and avoid letting its weekday threshold determine study feasibility by itself.

**Acceptance:** Completed/unnecessary work receives no new allocation. Updating the route changes remaining work. Missing availability or recruitment assumptions are identified rather than converted into a confident delivery schedule.

## The v0.5 interaction to build

The primary screen should answer four questions in order:

1. **What is already in place?** A compact set of relevant outcome checks, including work completed elsewhere.
2. **What needs attention?** Unresolved prerequisites and decision-critical blockers.
3. **What should I do next, and why?** One recommended action, the intended outcome and any prerequisite; a small number of justified alternatives where useful.
4. **How do I do it?** Start the guided activity, use the linked template, or open supporting methodology guidance.

The guide and template menus remain independently useful. Guided activity remains the main way to carry out a proposed action. At its end, review the captured result against the outcome, record any remaining blocker, then return to the updated next step.

Use stable outcome identifiers even when context changes the wording. Keep the stated project stage, assessed outcome state, activity execution, evidence references and escalation state distinct. One shared assessment result should feed the homepage, stage view, activity suggestions and timeline so they cannot disagree through separate rules.

For joining mid-project, assess only the dependencies needed for the proposed next action. “Unknown” should trigger a brief check, not an assumption that everything must be restarted.

## Example escalation rules to validate with the team

| Situation | First useful response | Escalation condition |
| --- | --- | --- |
| Decision/purpose missing | Clarify the decision with the product team | Nobody can own it, or it remains unresolved after framing |
| Intended users unavailable | Establish the access route and check what existing evidence can answer | Required direct evidence is blocked or a critical profile remains inaccessible |
| Deadline incompatible with the intended claim | Narrow the question/claim or review the deadline | The decision owner still requires an unsupported claim or infeasible scope |
| Findings cannot support the decision | Identify the particular missing or conflicting evidence | The gap cannot be resolved within the constraints and needs a decision on residual risk |
| Solution already fixed | Identify remaining decisions and a useful limited contribution | No meaningful choice can be influenced; decide whether to reframe, pause or stop |

These are proposed product rules, not approved organisational escalation policy. Confirm who owns each decision before embedding role-specific instructions.

## Order of work

**First: establish and agree the framework rules.** Map the source's branch points into outcomes, applicability, prerequisites, response options and stop/revisit conditions. Validate the map against real starting, mid-project and late-project examples.

**Then: implement the state and routing layer.** Build outcome assessment, applicability and next-action calculation together. Add persistent blocker handling. Preserve existing v1 project backups: keep notes, templates and activity history; do not silently treat an old completion flag as proof of every new outcome.

**Then: reconnect the interface.** Put outcome checks and the next action first. Make methodology guidance supporting help. Connect the guided-activity closeout and canvas review to the same assessment. Derive progress and remaining work from that assessment.

**Before release:** replace tests that merely enshrine the current guide hierarchy with scenario-based acceptance tests. Retain the existing persistence, escaping, legacy import, reset/Undo and export checks. Avoid adding more guides or templates until the route behaves coherently.

Contained early corrections include keeping relevant warnings visible, making missing-purpose checks explicit and clarifying the existing timeline. Those reduce confusion, but they do not replace the shared state/routing work.

## Minimum release scenarios

| Scenario | Required result |
| --- | --- |
| Brand-new project, purpose unknown | First task clarifies the decision and users; no premature method prescription |
| Mid-project with framing and plan already done | Acknowledge existing outputs; start at the next relevant gap |
| Analysis ready, evidence available | Recommend interpretation and coverage checks; no full restart |
| Findings shared, decision still blocked | Identify the blocker type and owner; offer targeted follow-up |
| Open project with no blocker | No mandatory constrained-alignment or blocker-resolution activity |
| Small urgent project | Feasible first action and bounded claim; no unsupported fieldwork promise |
| New quantitative population claim, access/time insufficient | Feasibility review and explicit decision on scope, deadline or claim |
| No user access | Persistent, relevant access action/limitation with a route to resolution |
| Critical segment missing among reachable profiles | Surface that gap rather than relying on aggregate access/counts |
| No baseline but improvement requested | Establish a comparison or bound the claim; do not certify improvement |
| All relevant outcomes met | Closeout/reuse recommendation and consistent progress/timeline |
| Context changes or v1 backup is restored | Preserve work, re-evaluate relevance and identify assessments needing review |
